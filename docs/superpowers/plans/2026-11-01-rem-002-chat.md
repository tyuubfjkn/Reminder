# REM-002 conversational confirmation implementation plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [x]`) syntax for tracking.

**Goal:** General conversation with explicit, proposal-bound consent before task writes; independent planned times; system-following time zone; a polished CC-owned desktop refresh.

**Architecture:** Keep Electron/React/SQLite and the manual v1 bridge. Extend assistant v1 with chat, proposal and cancelled replies and proposal-bound decisions. The model never authorizes a commit. Immutable normalized proposals live in bounded sessions; only confirmed writes have durable SQLite receipts. Main owns OS zone synchronization and renderer change notification.

**Tech Stack:** Node 24.16, Electron 45.2.1, ESM backend, React/TypeScript renderer. No new runtime dependencies.

**Spec:** docs/superpowers/specs/2026-10-31-reminder-design.md, REM-002 conversational revision. User authorized direct implementation with "推进" and added automatic system time zone.

## Global Constraints
- Codex owns shared contracts, backend, main/preload, tools/docs; CC owns apps/desktop/renderer/**.
- Every AI create/update/complete/reopen requires explicit confirmation of an exact visible proposal, including direct commands. Undo is an explicit user action; the renderer shows a detailed confirmation dialog first.
- Planned time is not deadline, notification time or automatic scheduling. Preserve manual task operation and existing data.
- Keep same-ID retries and atomic batch/undo revision protection. Never send keys or existing task notes to the provider.
- Conversation/proposals are memory-only: 50 sessions, 30-minute idle expiry; a proposal expires 10 minutes after creation. No live provider claim without a real configured key.
- System time zone refreshes at startup, before IPC operations, on resume and every 60 seconds. Stored instants/date-only values are not rewritten.

## Review Focus
- Lost replies and old proposal buttons must never confirm a newer proposal: exact proposal ID binding, immutable cached retries, durable confirmation receipt.
- Editing/cancelling/talking about another topic invalidates the old proposal; a failed edit must also revoke its old consent target.
- Task or system-zone changes during model work or between proposal and confirmation reject the whole batch.
- Deadline and planned time can each have a separate DST ambiguity on the same task; selections bind to operation and field.
- Schema-v2 Undo receipts without plannedAt remain usable after migration and restore plannedAt=null.
